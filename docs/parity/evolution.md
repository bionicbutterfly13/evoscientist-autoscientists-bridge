# EvoScientist parity audit: evolution and memory (paper §3.1, §3.2, §3.5, §4.5, §5.4, App. D)

Paper: arXiv 2603.08127. Code: [EvoScientist/EvoScientist](https://github.com/EvoScientist/EvoScientist/tree/e2eef14) @ e2eef14 (v0.3.8). Read-only audit.

Paths: `EvoScientist/...` paths are relative to the repo root. `SKILL:...` paths point to an **out-of-repo** installed EvoSkills copy at `~/.evoscientist/skills/` (commit 6d92ea5, per `~/.evoscientist/skills/.installed.yaml`). The repo does not bundle these skills. It names them only in prompt text (`EvoScientist/prompts.py:59-68`), and the user installs them from github.com/EvoScientist/EvoSkills. I list them because they are the only place the paper's IDE/IVE/ESE appear. They are LLM instructions, not code.

Bottom line: the repo has no coded Evolution Manager Agent, no M_I/M_E stores, no IDE/IVE/ESE logic, no embedding retrieval, and no ablation switches. What it ships instead is a generic memory system: per-turn and per-subagent "EvoMemory" workers that write profile files and typed observations, a self-linking observation graph, and AutoSkills. The paper's evolution mechanisms exist only as prompt text in the external `evo-memory`, `research-ideation` and `experiment-pipeline` skills.

## 2. Missing or divergent, ranked (by impact on reproducing the paper's results)

1. **No coded EMA or IDE/IVE/ESE (#2, #10-16, #28).** The paper's central mechanism, the one behind every RQ4 number and Fig. 2, is absent from the repo. It exists only as LLM instructions in an external, separately versioned skill pack, so a run's evolution behaviour depends on which skill commit is installed and on whether the orchestrator chooses to follow it.
2. **No M_I/M_E stores in the repo, and the skill's stores are workspace-local (#5-6, #9, #21).** The repo's memory (profile and typed observations) is not split into ideation and experimentation. The skill's `/memory/*.md` files land under `work_dir`, which in `--mode=run` is a fresh `runs/<name>`, so cross-task evolution can silently fail to carry over.
3. **No ablation switches (#24-27).** −IDE, −IVE, −all and −ESE cannot be toggled. The only toggles disable a different memory system, so Table 3 and Fig. 2 cannot be regenerated as specified.
4. **Retrieval is not embedding-based (#17-19).** Lexical ranking in the repo and LLM judgement in the skill replace mxbai-embed-large cosine top-k with k_I=2 and k_E=1. This changes which memories reach the prompt and how many.
5. **The EMA trigger and scope diverge (#3, #22).** Workers fire after every turn and subagent run, write at most 3 generic observations, and never see the (P, W) pair or I_top. The paper's single end-of-task distillation is not reproduced.
6. **The ESE success gate (#15).** The skill runs ESE only after all four stages pass. The paper distils from full trajectories regardless of outcome, so M_E would get fewer and more biased entries, which matters for the 34.39→44.56 execution-rate claim.
7. **The IVE "rule-based" check is LLM-judged and the skill extends IVE (#13-14).** With no coded budget counter, FAILED(NoExecutableWithinBudget) is not deterministic. The extra implementation-vs-fundamental classification changes what is written to M_I.
8. **Three agents vs six subagents, and one model (#1, #32).** The roles are re-cut (planner, research, code, debug, analysis, writing), and per-role models (Gemini for ideation, Haiku for code) are not configurable per subagent. This affects idea quality and code success-rate comparability.
9. **The two-stage pipeline is prompt-only (#4, #23).** G→I→P→C→W is a recommended skill sequence, not an enforced flow, and W is never wired into evolution.

## 3. Searched but uncertain

- **Whether the EvoSkills commit used for the paper matches the installed 6d92ea5.** I audited only the local install. The repo pins no skill version, and the upstream EvoSkills history was not checked.
- **Whether `langchain-ollama` is ever used for embeddings through a provider string.** I found no `OllamaEmbeddings` import or embedding call in `EvoScientist/`. A dynamic `init_*` path I did not trace is not ruled out, but nothing in the memory code consumes vectors.
- **How faithful the skill prompts are to Figs. 10-12.** Distinctive phrases match (`DEDUPLICATION`, `Actionable Memory`, `Do-not-repeat notes`, `NoExecutableWithinBudget`, `pipeline from raw input to tensor`), but I did not diff the skill's `paper-prompts.md` line by line against the PDF.
- **Daemon-mode persistence of `/memory/*.md`.** In daemon mode the workspace root is stable, so M_I/M_E should persist per workspace. I did not confirm whether the TUI or WebUI ever defaults to run mode for research tasks.
- **Whether the orchestrator reliably invokes `evo-memory` after ideation and experiments.** Only skill prose (`research-ideation` Step 6, `experiment-pipeline` handoff) requests it. Nothing in the repo checks or tests that it happens. `tests/` contains no evolution tests: `ideation` appears only as a path string in `tests/test_stream_utils.py:138,208`.
